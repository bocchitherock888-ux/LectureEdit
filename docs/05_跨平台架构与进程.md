# 05 · 跨平台架构与进程

## 1. 技术栈与决策理由

前端采用 React、TypeScript、Vite。桌面宿主采用 Tauri v2 与 Rust。转写输入框保持轻量受控编辑；资料块采用 Tiptap，公式通过 KaTeX 渲染。数据库采用 SQLite。实时识别放在独立原生进程，接口由 Rust 代理。

Tauri 的 sidecar 机制支持打包与启动按目标平台编译的外部二进制。[S14] 音频、文件系统和数据库本来就需要本机能力，将它们集中到 Rust 可以统一生命周期与权限。Electron 可作为 G0 后有证据的替代决策；更换需要记录安装体积、前端一致性、维护成本和迁移收益。

共享代码主要包括界面、文档模型、合并语义、持久化、调度和导出。音频权限、系统声音捕获、安装签名和系统凭据存储需要平台实现。

## 2. 进程图

```text
React / WebView
  ├─ 转写展示、编辑草稿、课堂资料、状态与设置
  └─ 类型化 Tauri commands / events
                  │
Rust 桌面宿主
  ├─ Command Router → 单写者 Domain Actor → SQLite
  ├─ Audio Capture → 无锁帧队列 → Archive Writer → PCM 音频块
  ├─ VAD / Segmenter → ASR Scheduler → Backend Adapter
  ├─ Asset Service / Export Service / Recovery Service
  └─ Worker Supervisor → 本机认证接口 → 原生模型进程
                                              └─ Qwen / whisper
```

WebView 接触经过类型校验的领域对象与受控资源 URL。录音帧、API 密钥、模型文件路径与任意 shell 能力保留在 Rust 内。

## 3. 线程与任务隔离

音频回调仅复制帧并写入有界队列。Archive Writer 负责顺序写盘和定期持久化。ASR Scheduler 只提交音频范围引用，避免大块音频穿过前端。Domain Actor 是唯一数据库写入者；耗时图像解码、导出和音频合并使用专用工作任务。

模型推理进程崩溃时，录音回调、写盘任务和前端继续存活。监督器记录失败、停止旧请求、增加 worker epoch，重新加载或提示切换本地后端。后台结果携带 epoch，旧进程迟到响应由领域层丢弃。

## 4. 推荐仓库结构

```text
apps/desktop/src/                 React 页面与组件
apps/desktop/src-tauri/src/
  commands/                      类型化入口
  domain/                        聚合、事件、合并与规则
  audio/                         公共帧管线与重采样
  platform/macos/                ScreenCaptureKit、权限
  platform/windows/              WASAPI、权限
  inference/                     调度、监督器、适配器
  storage/                       SQLite、迁移、备份
  assets/                        图片与附件安全处理
  exports/                       Markdown、HTML、课程包
packages/contracts/              由 Rust 类型生成的 TS 契约
packages/editor/                 草稿、资料编辑器与节点
packages/design-tokens/          CSS 与界面变量
native/                          锁定的推理源码与构建脚本
models/manifest/                 校验清单，仓库中只放清单
tests/                           领域、集成、E2E、故障和夹具

```

运行时下载的模型、用户课程与密钥均位于系统应用数据目录，不进入 Git。源代码仓库仅包含小型允许再分发的测试数据。

## 5. 后端统一接口

所有适配器实现 `capabilities`、`load`、`transcribe_snapshot` 或 `push_audio`、`finalise`、`cancel`、`unload`。只有 native_streaming 能力开启时才调用 `push_audio`。

输出统一为完整机器快照、音频区间、语言信息、可选时间戳以及错误类型。置信度是可选项；模型没有可靠置信度时，界面依据“临时结果”“已稳定”等真实状态提示，禁止生成伪百分比。

适配器负责模型特有标签、模板和特殊 token 的解析。课堂转写不调用工具、浏览器、代理或任意代码执行能力。

## 6. 本机服务模式

优先让 Rust 启动一个持久 llama-server，以便减少 ABI 绑定与崩溃扩散。端口随机分配并进行占用检测；绑定 `127.0.0.1`，生成每次启动独立的随机凭据。API 密钥文件仅当前用户可读，启动后按运行库实际要求管理生命周期。

健康检查可用于检测加载状态；llama-server 的健康接口本身不要求认证，因此还需发送带凭据的短探测请求，核实正确服务与模型已经就绪。[S07] WebView 通过 Rust 调用服务，前端持有领域接口即可。

冻结的构建必须关闭 Web UI 和无关服务能力。命令行参数通过数组传递；所有可执行文件、模型路径和日志目标均从受控配置产生。

## 7. 平台捕获适配器

通用麦克风路径可评估 CPAL；系统声音仍采用各平台专门接口。[S17] macOS 使用 ScreenCaptureKit 实现受权限控制的系统或应用音频，Windows 使用 WASAPI loopback 实现输出设备捕获。[S18][S19]

实体课堂麦克风与线上课程系统声音是两个清晰选择。首版每次使用一个来源，数据模型预留多轨字段。双轨混音、回声抵消与说话人识别分别安排开发，避免将两种音源直接叠加后造成重复声音。

## 8. 打包与发布

macOS 首轮构建 arm64 DMG，应用与嵌入的原生推理程序一起签名，配置麦克风用途说明，并验证 ScreenCaptureKit 的权限流程。公开分发需完成合适的签名与公证流程。[S15]

Windows 首轮构建 x64 安装程序，包含所需运行库与签名后的原生程序；测试标准用户安装、升级、卸载和安全软件提示。模型保持独立安装与更新，卸载程序询问是否保留课程和模型。

CPU 基础版本优先建立；GPU 加速包按测试结果提供。每个平台在自身系统上构建和运行原生烟雾测试，禁止用“另一平台源码可编译”替代真实运行验收。

## 9. 更新策略

应用、推理运行库、模型与数据库分别有版本号。应用更新先检查兼容性，正在录音时只下载更新，安装留到会话安全结束。模型更新校验完成后原子切换清单；旧模型在无任务使用后删除。

数据库迁移前创建一致备份，迁移失败恢复原版本并展示错误。设计仅支持经过测试的升级路径；旧应用打开新数据库时应提示需要更新，保持文件完整。
